# terraform-provider-oncall

Terraform/OpenTofu provider for [oncall](https://github.com/observiply/oncall).
Built with [terraform-plugin-framework](https://github.com/hashicorp/terraform-plugin-framework).

Status: all six resources and five data sources exist
(`tfprovider-07-provider-resources.md`); the API gaps that blocked publishing
(`tfprovider-05-api-gaps.md`) are closed. Release tooling (`.goreleaser.yml`,
`terraform-registry-manifest.json`, `tfplugindocs`) is scaffolded, but this
provider has **not been published to the public Terraform Registry yet** —
see "Releasing" below for what's still required (a GPG key with an assigned
owner, and provider-side acceptance tests per
`tfprovider-09-testing.md`, which are not done). Until then, install it
locally via `dev_overrides` (below).

## Layout

```
main.go                     provider server entrypoint (providerserver.Serve)
internal/
  client/                   generated from oncall's docs/swagger.json — do not hand-edit
    swagger.json            vendored copy, pinned; CI diffs it against oncall main
    generate.go             //go:generate oapi-codegen directive
    client.gen.go           generated output
  provider/
    provider.go             schema, config (endpoint/token), validation, auth probe
examples/                   used by tfplugindocs to generate docs/
  complete/                 a realistic multi-resource setup — what people copy
docs/                       generated by tfplugindocs — do not hand-edit once populated
templates/                  tfplugindocs overrides (index.md.tmpl)
.goreleaser.yml              release build: platform matrix, checksums, GPG signing
terraform-registry-manifest.json  declares protocol version 6.0 to the registry
```

## Generating docs

```bash
go generate ./...   # also regenerates internal/client — see below
```

`tfplugindocs` reads schema `Description` strings and `examples/`, so treat
those descriptions as user-facing documentation, not code comments. CI's
`docs-drift` job fails if `docs/` is out of date with the schema.

## Building

```bash
go generate ./...   # regenerate internal/client from swagger.json
go build ./...
go vet ./...
golangci-lint run
```

## Updating the vendored API spec

`internal/client/swagger.json` is a pinned copy of oncall's `docs/swagger.json`,
not a live fetch — a silently-updated spec regenerating the client mid-PR is how
you ship a provider that compiles and lies about the API it talks to. CI's
`spec-drift` job diffs it against oncall `main` on every push/PR. To pick up an
intentional oncall API change:

```bash
cp /path/to/oncall/docs/swagger.json internal/client/swagger.json
go generate ./...
git add internal/client/swagger.json internal/client/client.gen.go
```

## Local development (no registry, no publish step)

Build the provider and point Terraform/OpenTofu at the binary instead of a
registry release, via `dev_overrides`. This repo is developed against
[OpenTofu](https://opentofu.org) (`~/.tofurc`); the same config works for
Terraform under `~/.terraformrc` — the CLI config block is identical, only the
env fallback name differs (`TF_CLI_CONFIG_FILE` works for both).

```bash
go install .

cat >> ~/.tofurc <<'EOF'
provider_installation {
  dev_overrides {
    "observiply/oncall" = "/Users/<you>/go/bin"
  }
  direct {}
}
EOF
```

`go install .` places the binary at `$(go env GOPATH)/bin/terraform-provider-oncall`
— use that directory (`go env GOPATH`, then append `/bin`) as the override path,
not the repo directory. With the override in place, `tofu plan`/`apply` uses your
locally built binary directly; skip `tofu init` for this provider (it will
complain that `observiply/oncall` isn't a real registry provider yet — that's
expected and harmless with dev_overrides active).

## Configuration

```hcl
provider "oncall" {
  endpoint = "https://oncall.example.com" # or ONCALL_ENDPOINT
  token    = var.oncall_token             # or ONCALL_TOKEN (Sensitive)
}
```

- `endpoint` is oncall's base URL. Don't include `/m2m/api/v1` — the provider
  appends it, and tolerates the common mistake of pasting the full path anyway.
- `token` must be an oncall-issued API token (`oncall_pat_...`, minted from the
  oncall UI's Settings -> API tokens). An authentik token or a trigger ingest
  token will be rejected at configure time with a specific error, not a generic
  401 from deep in a resource call.
- Prefer the env vars over a token literal in `.tf` files, which end up in
  version control.
- `Configure` runs an auth probe (`GET /admin/teams`) once, up front, so
  credential problems surface as one clear error instead of N confusing
  per-resource failures. 401 vs 403 vs 503 are distinguished — see
  `internal/provider/provider.go`.
- The token is **scoped to oncall** (not authentik or any other Observiply
  product) and **expires** (90 days by default, 365 max) — both bound the
  blast radius of a leak, but neither makes it acceptable. See oncall's admin
  token inventory for expiring-soon tokens, and rotate before a pipeline finds
  out at 3am: issue a new token, update the CI secret, verify a plan, then
  revoke the old one.

## Secrets

`terraform.tfstate` is not a safe place for the values the oncall API only
ever accepts and never returns — `oncall_integration`'s outbound auth secret
chief among them. This provider uses Terraform's **write-only attributes**
(`secret_wo` / `secret_wo_version` on `oncall_integration`) for that value:
the secret is available during `apply` but is never written to state or plan
files. The paired `_version` integer is the only thing the provider can diff
against, since the API never echoes the secret back — bump it to send a new
value; changing `secret_wo` alone does nothing.

**Requires Terraform or OpenTofu >= 1.11** (declared in
`examples/provider/provider.tf`) — write-only attributes are not available on
older CLI versions.

Trigger ingest tokens are handled differently, deliberately: `oncall_trigger`
exposes `token` as an ordinary (if `Sensitive`) computed attribute, populated
once from the one-time create response and never re-fetched or rotated by
this provider. `POST /admin/triggers/{id}/rotate-token` also returns its
value exactly once, so unlike the integration secret there is no way to model
rotation without a value landing in state somewhere — this provider does not
try. Rotate trigger tokens out-of-band (the oncall UI, or a one-off script);
if you want it in Terraform anyway, `terraform_data` with a `local-exec`
provisioner works, having made an explicit choice to put a secret in state.
See `tfprovider-08-secrets-and-rotation.md` in oncall's `plan/` for the full
reasoning.

Even with every secret excluded, state still holds real on-call topology —
schedule names, team ids, user ids, trigger templates. Nothing PII (oncall's
API redacts that at the boundary), but treat it accordingly: use a remote
backend with encryption for anything beyond a local test.

## Releasing

`.github/workflows/release.yml` runs GoReleaser on any `v*` tag push, producing
the standard platform-matrix binaries, `SHA256SUMS`, a detached GPG signature
over the checksum file, and the versioned `terraform-registry-manifest.json`
copy the Terraform Registry expects — all per `tfprovider-10-release.md` in
oncall's `plan/`.

**Not yet done, and required before the first real tag:**

- **A GPG signing key, with an owner.** The private key and passphrase go in
  this repo's `GPG_PRIVATE_KEY` / `PASSPHRASE` Actions secrets; the public
  half is uploaded to the Terraform Registry account that publishes this
  provider. Decide who holds the private key and how it's rotated *before*
  generating it — rotating a published provider's signing key is a real
  operational chore, and "the person who set it up left" is the failure mode
  to avoid.
- **Provider-side acceptance tests and the PII guard test**
  (`tfprovider-09-testing.md`) — not started as of this writing. Don't
  publish `v1.0.0` to the public registry ahead of these; a `v0.x` tag for
  internal dogfooding via `dev_overrides` doesn't need them first.

Once a key exists and the registry app is set up: register the repo with the
Terraform Registry (Publish → Provider), then `git tag vX.Y.Z && git push
--tags` — the workflow does the rest.

## CI

- `build`: `go generate` (fails the build if the committed `client.gen.go` is
  stale relative to `swagger.json`), `go build`, `go vet`, `golangci-lint`.
- `spec-drift`: diffs the vendored `swagger.json` against oncall `main`.
- `docs-drift`: fails if `docs/` is stale relative to schema descriptions and
  `examples/`.
- `tofu-fmt`: `tofu fmt -check -recursive examples/`.

Runs on standard GitHub-hosted runners — this is a public, standalone repo, not
part of oncall's internal ARC Kubernetes runner set (see oncall's `AGENTS.md`
for why that distinction matters there).
