# oncall Provider

Manages oncall schedules, layers, triggers, and integrations. Credentials are an oncall-issued API token (oncall_pat_...), not an authentik identity of the provider's own.

## Getting a credential

Log into oncall, go to **Settings → API Tokens**, click **Create**, and copy the
token — it is shown exactly once. Set it as `ONCALL_TOKEN` (or the provider's
`token` argument, though the env var keeps it out of `.tf` files and version
control).

The token is:

- **scoped** to oncall and to your teams — it cannot reach authentik or any
  other Observiply product, and it only sees the teams the issuing user
  belongs to;
- **time-limited** — 90 days by default, 365 days maximum;
- **tied to your account** — acting as you, and (once the delegated-refresh
  stage lands) revoked automatically if your upstream account is disabled.

No authentik admin access is required to get one — that's the point.

**Rotation runbook** (this is the failure people actually hit, not the
90-day cap in the abstract): before the current token expires, issue a new
one from the same Settings page, update the secret in wherever your CI or
`ONCALL_TOKEN` is set, run a `plan` to confirm it authenticates, then revoke
the old token from the same page. Don't revoke first — a mid-rotation gap
fails every pipeline run until the new secret propagates.

## Teams are not managed by this provider

An administrator creates and maps teams in the oncall UI (Teams → Manage).
This provider only manages resources *within* teams that already exist —
there is no `oncall_team` resource, only the `oncall_team` /
`oncall_teams` data sources to look one up by name.

## Sharing and `owner_team_id`

Every schedule, trigger, and integration has an `owner_team_id`, set once at
creation from `team_ids`. The owner team controls sharing forever — only a
caller with `share` in the owner team can change who a resource is shared
with — so `owner_team_id` is **immutable** and is always implicitly present
in `team_ids`, whether or not you list it explicitly.

## Secrets are write-only

`oncall_integration`'s outbound auth secret uses Terraform's write-only
attribute pattern (`secret_wo` / `secret_wo_version`): the value is sent on
apply but never written to state or read back from the API. This requires
**Terraform or OpenTofu >= 1.11**.

## Example Usage

```terraform
terraform {
  # >= 1.11 for write-only attributes (oncall_integration's secret_wo).
  required_version = ">= 1.11"

  required_providers {
    oncall = {
      source = "observiply/oncall"
    }
  }
}

# endpoint and token are both settable via ONCALL_ENDPOINT / ONCALL_TOKEN instead
# — prefer that over committing a token in a .tf file.
provider "oncall" {
  endpoint = "https://oncall.example.com"
  token    = var.oncall_token
}

variable "oncall_token" {
  type      = string
  sensitive = true
}
```

See `examples/complete/` in the provider's repository for a fuller setup —
a schedule with two rotation layers, a trigger with routed targets, and an
integration, all shared across two teams.

## Version compatibility

This provider targets oncall API `v1` and checks that on every `Configure`
via oncall's unauthenticated `GET /version` endpoint, before any resource or
data source runs:

- an oncall install old enough to predate `/version` itself (a 404) fails
  with a clear "upgrade oncall" error rather than a bare 404 on the first
  resource;
- an oncall reporting a different `api_version` fails with a clear
  "use a provider release built for that API version" error.

As of this release oncall's API has had no changes since `v1`, so any
currently self-hosted install passes this check — the gate exists for the
day a future provider or oncall release moves the contract, not because
there's an incompatibility to guard against today.
